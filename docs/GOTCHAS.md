# SuperAudio — Known gotchas

> The canonical numbered list of hard-won lessons. Referenced as **gotcha #N** throughout the codebase, in `docs/DECISIONS.md`, and in PR descriptions. Add new entries here (do not retire numbers — they are stable references).

For load-bearing principles and the project brief, see [../CLAUDE.md](../CLAUDE.md). For the "why we chose X" record, see [DECISIONS.md](DECISIONS.md).

---

1. **Sonos sync is loose by design.** The Playbar has ~200ms+ of internal buffering you cannot bypass via UPnP. Don't try. Expose it as an offset and move on.
2. **AirPlay 1 encryption uses a known public RSA key** that's just hardcoded everywhere. It's not actually a secret — Apple stopped enforcing it years ago, but old receivers still expect the handshake. shairport-sync has the key.
3. **CoreAudio process tap entitlements are tricky under Personal Team signing.** Plan A: `com.apple.security.device.audio-input` + ad-hoc local signing under your free Apple ID. Plan B (if Plan A returns `kAudioHardwareUnsupportedOperationError`): install [BlackHole](https://github.com/ExistentialAudio/BlackHole) as a virtual audio device, route system output through it, capture from BlackHole as a regular input device. Decide which path Phase 1 is on within Day 1. Don't burn weeks fighting Apple's signing for a POC.
4. **mDNS on macOS** sometimes caches stale records. Use `dns-sd -B _raop._tcp` from terminal to sanity-check what's actually advertising.
5. **AVAudioConverter to AAC has ~50ms+ encoder latency.** Account for it in the Sonos offset calc.
6. **DRM content plays silent.** Apple Music with FairPlay won't produce audible output through the tap. Expected. Confirm by testing with Spotify free tier first; don't chase a "silent output" bug.
7. **AirTunes/103.x RECORD hangs without NTP timing replies.** RAOP receivers (B&W A5/A7 confirmed, likely all AirPort-Express-derived hardware) send 32-byte timing-channel requests (RTP-shaped, payload type `0xD2`) to the sender's advertised `timing_port` after SETUP. The sender MUST reply with PT `0xD3` NTP-format responses or RECORD silently never ACKs. This was the root cause of an entire night of failed RECORD attempts. The handshake is in `Sources/SuperAudioAirPlay1/RTSPClient.swift` (`RAOPTiming.buildResponse` + the `timing.onReceive` closure).
8. **`NWListener` with `NWParameters.udp` silently swallows inbound datagrams.** `newConnectionHandler` does not fire reliably for UDP flows even when the kernel is demonstrably delivering packets to the bound port. We worked around this with BSD `socket()` + `recvfrom()` in a background thread (see `UDPSocket` class in `Sources/SuperAudioAirPlay1/RTSPClient.swift`). If you find yourself debugging missing UDP receive on macOS, this is the first thing to check.
9. **OSLog can lie about timeouts.** Our `RTSPClient.receiveAll` reported "RTSP timed out" while tcpdump showed the server had replied with a real `500` just after the timeout fired. When client-side logs say "timed out" but the server has had time to reply: **capture the wire, don't trust the log.**
10. **AirPlay 1 audio requires REAL compressed ALAC. The verbatim/escape path is silently rejected.** The ALAC spec defines an `escape=1` "uncompressed" element that wraps raw 16-bit PCM in a thin ALAC frame. Apple's own open-source encoder uses this as a fallback when compression fails to shrink the data. **B&W A7 / A5 firmware silently drops these frames.** Music.app never sends them. Confirmed via tcpdump diff: Music.app emits variable-size 642–1117-byte packets (compressed); our verbatim mode emitted fixed 1412 bytes and produced silence even though every other layer (RTP, AES, sync) was byte-correct. **Fix:** use `AVAudioConverter` with output format `kAudioFormatAppleLossless` — it produces compatible compressed ALAC natively with parameters (pb=40, mb=10, kb=14) matching standard SDP fmtp lines. See `Sources/SuperAudioAirPlay1/RTPSender.swift` and DECISIONS.md 2026-05-14 Finding 1.
11. **AirPlay 1 sync packets MUST come from the source port advertised in SETUP's Transport header.** The receiver `connect()`s its control UDP socket to (our_IP, our_advertised_control_port). Anything from a different source port is kernel-rejected at the receiver with ICMP "port unreachable" before the speaker's app code sees it. We discovered this with `probe/PortProbe.swift` — UDP probes during a live session showed the control port returned ICMP-closed to any non-matching source. **Fix:** `RTSPClient.sendOnControlSocket(_:toHost:port:)` routes sync packets via the existing BSD socket bound to the advertised local control port. Audio packets stay on `NWConnection.udp` (audio doesn't source-validate). See DECISIONS.md 2026-05-14 Finding 2.
12. **Each `Scripts/build_app.sh` invalidates TCC audio-recording permission.** macOS hashes the executable and revokes permission when the hash changes. Re-launching the existing `.app` bundle preserves the grant. Workflow: prefer `open SuperAudio.app` over `Scripts/build_app.sh && open …` when you haven't changed code. When you do rebuild, expect one Terminal/SuperAudio recording prompt; accept and continue.
13. **`killall SuperAudio` mid-stream leaves the speaker stuck.** If the app process is killed before sending TEARDOWN, the speaker holds its RTSP TCP port closed for 1-5 minutes until its internal session timeout fires. Workarounds: (a) physically power-cycle the speaker, (b) wait. **Permanent fix shipped 2026-05-14**: `SIGTERM`/`SIGINT` handlers in `AppDelegate.installSignalHandlers` route through `NSApp.terminate(nil)` → `applicationWillTerminate(_:)` which sends RTSP TEARDOWN + Sonos `Stop` before exit.
14. **Controller identifier headers (`Client-Instance` / `DACP-ID` / equivalents) MUST be per-`RTSPClient` instance, NOT static-per-process.** Originally `RTSPClient.staticClientInstance` was a `private static let` — every concurrent session shared one identifier. B&W AP1 receivers track session state by controller ID; when A5 and A7 sessions presented the same ID simultaneously, A7's firmware refused the cold connection (treating it as a stale prior session). The fix is one line — `private static let` → `private let`. Generalized rule for future protocols (AP2's `Active-Remote`, Cast's session tokens, anything that names "the controller"): if our model is "each session = independent controller," the identifier must be per-session-instance. iTunes shares one identifier across its many speakers because it IS one controller; SuperAudio's model differs. See DECISIONS.md 2026-05-15 (night) entry section 2.
15. **Network blips on RTP UDP are invisible to the sender.** UDP packet loss isn't reported; the receiver just stops getting audio. Idle RTSP TCP also doesn't fail until we try to send. **Detection requires active probing.** `AirPlay1Session.run` watches `RTSPClient.lastTimingPacketUnixTime` — receivers send PT `0xD2` timing requests every ~1 sec while actively playing, and we treat absence >15 sec as "receiver dropped off the network." `HealthFlag.lost = true` → main loop unwinds → supervisor retries. Don't trust "audio is still flowing because UDP didn't error" — it WILL silently dead-air on Wi-Fi blips without this. (The earlier OPTIONS-over-TCP approach produced false positives when the RTSP socket was idle during streaming; replaced 2026-05-16.)
16. **AirPlay 1 receivers clamp far-future NTP scheduling to their internal buffer depth.** B&W A5/A7 announce `Audio-Latency: 4096` (≈93 ms buffer). When you set `RTPSender.manualOffsetSeconds = 5.0` to delay playback, the receiver does NOT honor the 5-sec future NTP — it plays the packet ASAP regardless. Empirically tested 2026-05-17 across slider values 0/2000/4040/5500/6000 ms: zero audible difference. The receiver-side NTP scheduling is a hint, not a hard schedule. **Fix:** shift audio at the *sender* instead — `AudioBroadcaster.subscribe(id:delaySeconds:)` holds chunks in a per-subscriber `Task.detached { sleep(delay); yield }` before delivery. Receiver gets packets `delay` seconds after capture and plays them on arrival. Net audible delay = the broadcaster delay. Required: defensive `AudioChunk.makeCopy()` (CoreAudio buffers recycle) + `presentationHostTime` rewrite to `original + delayHostUnits` (otherwise downstream sync NTP math lands in the past and the receiver rejects packets). See `Sources/SuperAudioCore/AudioBroadcaster.swift` + DECISIONS.md 2026-05-17.
17. **Sonos playback timing is encrypted at the wire level, not just undocumented.** SuperAudio cannot shift Sonos playback forward or backward from outside Sonos's own ecosystem. AVTransport exposes `Seek` / `RampToVolume` / etc. — **no timing-shift action**. The Sonos Android app's 75–2000 ms "line-in delay" slider is implemented via encrypted UPnP traffic; the most thorough public Sonos-API reverse-engineering project (`svrooij/node-sonos-ts`) explicitly gave up. See [node-sonos-ts#139](https://github.com/svrooij/node-sonos-ts/issues/139) — *"No public API. Cannot be done because Sonos doesn't have a public api for this... traffic analysis showed that part seems to be encrypted."* **Don't burn weeks trying to reverse-engineer it.** Practical implications: (a) the Sonos Δ slider in our menu is informational, not actionable (it's been replaced with a caption); (b) the only lever for Sonos-vs-AP1 sync in the Mac app is delaying the AP1 sinks (via gotcha #16's sender-side mechanism) to match Sonos's intrinsic buffer floor; (c) in the Hub Stick / Hub Pro product, this is a non-issue — Sonos is the TV's primary speaker (optical co-recipient), not our sink. See DECISIONS.md 2026-05-16 + 2026-05-17.
18. **Session-overlap state-clobber when sessions for the same sink overlap.** A rapid toggle off→on cycle (or supervisor restart) can produce two `AirPlay1Session.run` instances for the same sink. The old session's slow async cleanup (especially TEARDOWN that times out at 4+ sec) runs its `defer` block AFTER the new session has already started — wiping setters and active-flag the new session just registered. Manifests as "speaker is playing audio but menu shows unchecked / slider doesn't drive volume." **Fix:** every `AirPlay1Session.run` captures a `sessionNonce: UUID` at start; defer asks `SessionState.endSessionIfStillCurrent(sinkID:nonce:...)` before mutating shared state. If a newer session owns the sink, the defer is a no-op. Generalized rule for any future per-sink state mutation: **gate on nonce or skip the mutation**. See `Sources/SuperAudio/SessionState.swift`'s `currentNonce(for:)` + `endSessionIfStillCurrent`.
19. **Supervisor must distinguish "never connected" from "connected then died."** A naive "retry on any failure" loop produces a retry storm for AirPlay receivers that NEVER accept the prompt (other people's Macs in mDNS, dormant AirPort Express, etc.). Observed 2026-05-17: Derek's MacBook Air in `wantedActive` retried every 2 → 5 → 15 → 30 → 60 sec forever, eating Wi-Fi bandwidth our real speakers needed. **Fix:** `AirPlay1Session.run` and `SonosSession.run` return `SessionState.SessionExitReason` with four cases: `.cleanExit` (user-cancelled, exit loop), `.networkLost` (mid-stream blip, retry indefinitely), `.failedAfterAudio` (audio worked then died, retry indefinitely), `.failedBeforeAudio` (never connected — count against retry cap). Supervisor caps at 3 consecutive `.failedBeforeAudio`, then removes the sink from `wantedActive` entirely. Manual user click required to re-attempt. See `SessionState.superviseSession` + DECISIONS.md 2026-05-17.
20. **Ambient music cannot be a cross-correlation reference signal for sync measurement.** Tested 2026-05-18: cross-correlation engine (Accelerate vDSP FFT) had `SNR=20+` (rock-solid statistical lock) but returned lag values inconsistent with what the math said they should be. Diagnosis: music has rhythmic + harmonic structure that creates **spurious correlation peaks every beat / chord interval**. The "true" peak at the speaker's actual lag is sometimes weaker than spurious peaks elsewhere. Pro audio measurement (Smaart, REW, ARTA) use **chirps** (linear sine sweeps) for exactly this reason — chirps have near-flat autocorrelation, giving one clean unambiguous peak. **Fix:** `ChirpGenerator.linearSweep(200 Hz → 8 kHz, 1 sec)` injected into `AudioBroadcaster` via chunk-PCM overwrite (`applyChirpIfActive`). All subscribers play the chirp; mic correlates against the known chirp signal. If you ever consider "well, can't we just use the music that's playing?" — no, you cannot. See `Sources/SuperAudioCore/ChirpGenerator.swift` + DECISIONS.md 2026-05-18. (Superseded as default by MLS in M6.4 Phase 2b — see DECISIONS.md 2026-05-21.)
21. **AVAudioEngine first input-format query on macOS takes ~3 seconds.** First call to `input.outputFormat(forBus: 0)` (inside `MicCapture.capture`) triggers macOS to fully initialize the audio subsystem. The 3-sec stall happens BEFORE `installTap` + `engine.start` execute, so any `await` chain that schedules a chirp injection in parallel will fire the chirp before the mic actually starts recording. Symptom (2026-05-18): "first per-speaker measurement always returns near-zero lag; subsequent measurements are correct." **Fix:** at the start of any orchestrator that does multiple sequential mic captures, do a 500 ms throwaway `MicCapture.capture(duration: 0.5)` to warm the audio subsystem. Subsequent captures are instant because the OS keeps the subsystem live. See `MicCalibrator.runFullCalibration`'s warmup step.
22. **`SessionState.sinkOffsetsMs[id]` is empty until user touches a slider this session — read via `offset(for:)` instead.** Persisted offsets live in UserDefaults, NOT in the in-memory dict. The dict only fills on slider drags or programmatic `setOffset` calls. Code that needs the *current* offset (which may be the persisted value from a previous session) must use `SessionState.offset(for: sinkID)` which falls back to `UserDefaults.standard.integer(forKey: "sinkOffset.\(id)")`. 2026-05-18 calibration bug: `MicCalibrator` read `sinkOffsetsMs[id] ?? 0`, saw 0, applied delta as new offset, and reset A5 from user-persisted 3085 ms to 1543 ms. Generalized rule for any future per-sink state with persistence: the public accessor (`offset(for:)`, `volume(for:)`, etc.) is the source of truth, not the private dict.
23. **Auto-correctors restart the AirPlay 1 receiver on every offset change — the "flaky speaker" is actually a corrector-induced reconnect loop.** Symptom (2026-06-05, B&W A5 "Spacelab Audio"): the A5 keeps "failing and reconnecting" roughly every 13 s. The speaker is healthy — it pings, advertises `_raop._tcp`, and RECORDs `200 OK` the whole time. The loop is caused by the **automatic offset correctors**: `MicCalibrator` ("Mic Calibrate (auto)") and the **armed** `PassiveSyncMonitor` each retime the sink on every cycle, and an AP1 retime is a session restart. **Mechanism (builds on gotcha #16):** the A5 clamps NTP scheduling to its ~93 ms buffer, so the offset is applied *sender-side* as an `AudioBroadcaster` delay; a large retime briefly starves/silences the receiver, the health monitor (gotcha #15) reads the dead-air as a dropped receiver, and tears down + re-RECORDs. `MicCalibrator` also *explicitly* restarts the AP1 sink after applying. So every corrector apply — even a correct one — costs a restart, and a *continuous* corrector costs one per cycle. Confirmed from live OSLog (corrector apply timestamps line up 1:1 with session restarts). Also note the mic value can't be trusted: mic-based auto-cal wanted ~4200 ms while the by-ear-correct value was ~3050 ms (~1.2 s off, because mic position ≠ listening position). **Fix/workaround:** for AP1, use a **static manual offset set by ear** with **all correctors off** — Passive Sync in observe-only mode, never run Mic Calibrate (auto). No corrector touches the offset → the A5 never restarts → it stays connected and in sync (re-tune by ear occasionally as the Sonos buffer drifts). Hands-free continuous retiming awaits **AP2 (M12)**, which is smoothly delay-controllable in place and doesn't restart on a retime. See DECISIONS.md 2026-06-05.
