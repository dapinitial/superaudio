2The pipeline

Four layers, strict dependency direction, every layer testable in isolation.

NETWORK
macOS Bonjour daemon
Multicast DNS service discovery. Already running on every Mac. We talk to it via NWBrowser, no entitlement required, no manual sockets.
_raop._tcp · _sonos._tcp
PROTOCOL
Per-protocol discoverers
One SinkDiscoverer implementation per protocol family. Owns its own NWBrowser, parses its own TXT record, filters self-advertisement of the host Mac, emits events into an AsyncStream<SinkChange>.
AirPlay1Discoverer · SonosDiscoverer
CORE
SinkRegistry & DiscoveredSinks
App startup registers each discoverer with the central SinkRegistry. A single @Observable DiscoveredSinks reduces every discoverer's AsyncStream into one live array, deduplicated, ordered.
SuperAudioCore
UI
SwiftUI MenuBarExtra
The menu bar dropdown binds to DiscoveredSinks.shared.sinks via @Observable. When a new SinkChange.added propagates, the menu re-renders. This is the magic that makes "live discovery" feel inevitable rather than engineered.
MenuBarView.swift

Dependency direction (enforced by Package.swift)

  • SuperAudioCore depends on nothing project-internal. Pure Swift + Apple frameworks.
  • SuperAudioDiscovery depends on Core only. Shared discovery primitives.
  • SuperAudioAirPlay1, SuperAudioSonos each depend on Core + Discovery. They never import each other.
  • SuperAudio (the app) depends on everything and wires it together at startup.

3The event model — why SinkChange matters

A small data-model decision that paid off immediately.

Each discoverer emits a stream of SinkChange events:

public enum SinkChange: Sendable {
    case added(SinkDescriptor)
    case updated(SinkDescriptor)
    case removed(SinkID)
}

The alternative — emitting full lists of "current sinks" on every change — would have been simpler to write but worse on three counts:

ConcernFull-list streamChange stream (chosen)
UI updatesDiff a list vs the previous list every timeApply one change at a time
ResilienceA brief blip looks like "lost everything, regained everything"Blip is a tidy .removed + .added pair
AnimationHard to know what actually changed for fade-in/outFree — UI sees the exact event
CompositionList-merging across N discoverers gets tangledEach discoverer's stream is independent; reducer does the work
The blip at 18:09:02 proved it. The A5 dropped off mDNS for 2 seconds, then re-announced. Our UI showed "removed", then "added", and the user saw it in real time. With a full-list model, this would have flickered or been hidden entirely.

4What this proves about the architecture

Discovery was the first place the case study's extensibility claims met real hardware.

Win 1

The protocol modules never import each other.
SuperAudioAirPlay1 doesn't know SuperAudioSonos exists. They only share the SinkDiscoverer contract from Core. Future SuperAudioAirPlay2, SuperAudioChromecast, SuperAudioBluetooth drop in next to these without touching anything.

Win 2

Same NWBrowser pattern works for two protocols.
Both AirPlay 1 (_raop._tcp) and Sonos (_sonos._tcp) advertise via Bonjour. We initially planned SSDP for Sonos; switching to Bonjour eliminated a multicast-entitlement headache and halved the code. Cleaner outcome than the case study originally planned.

Win 3

The UI doesn't know which protocol it's showing.
MenuBarView reads from DiscoveredSinks and renders SinkDescriptors. The descriptor knows its protocolKind for display, but the view never branches on it. Adding a protocol adds rows; it doesn't add cases.

Win 4

Filtering belongs in the UI, not the discoverer.
First pass filtered Macs/iPhones at the discoverer level. Better: discoverers emit everything they find; UI applies isLikelySpeaker heuristic + a @AppStorage-persisted toggle. Diagnostics and UX share the same data.

Win 5

Live discovery cost zero extra engineering.
We didn't build a polling loop, a periodic refresh, or a "scan now" button. The browser is always open; the stream is always live; the UI always reflects current state. This is what "reactive" actually buys you.

Win 6

The Phase 1 gate isn't even the destination.
The official Phase 1 gate is "audio out of one B&W speaker for 30 min, no drops." Tonight covered discovery only, which was scoped as one bullet in Phase 1. The fact that discovery was clean enough to deserve its own commit, its own tag (v0.2-discovery), and its own doc says we're building above the planned bar.

5What this lets us add without touching Core

The extensibility model isn't theoretical anymore. Here's exactly how each addon slots in.

ProtocolModuleDiscoveryHard partEffort
AirPlay 2 SuperAudioAirPlay2 _airplay._tcp via Bonjour (already seen on the LAN) HomeKit-style pairing — SRP + Curve25519 2–3 weeks
Chromecast SuperAudioChromecast _googlecast._tcp via Bonjour Protobuf over TLS, CASTV2 protocol 2–3 weeks
Bluetooth A2DP SuperAudioBluetooth Enumerate paired devices via IOBluetooth macOS allows only one A2DP output at a time; multi-out needs virtual-device routing 2 wks single / longer multi

For each: a new directory under Sources/, one line in AppDelegate.registerSinkDiscoverers() gated by LicenseManager.isEnabled(.airplay2), and ship. No edits to Core, no edits to other protocol modules, no edits to the UI. Same exact pattern that produced tonight's three-speaker menu.

The commercial track's $5 per-protocol addon pricing model isn't wishful thinking. The architecture genuinely lets a future contributor build SuperAudioChromecast in isolation, license-gate it, and have it appear next to Den · Sonos in users' menus without touching a single existing file.

6Decisions made tonight

Worth recording for future-us.

Bonjour over SSDP for Sonos discovery

Original case study said Sonos uses SSDP. True — but Sonos also advertises via Bonjour as _sonos._tcp with full descriptor URL in the TXT record. Using Bonjour means:

  • Same NWBrowser pattern as AirPlay 1 (one mental model, less code)
  • No multicast entitlement (com.apple.developer.networking.multicast) needed
  • Room name comes free in the service instance name (no XML fetch required for discovery)
  • SSDP code we'd written sits cleanly in git history if some future UPnP device needs it

Executable name rename: SuperAudioApp → SuperAudio

The bundle was registering twice in macOS Menu Bar Settings — once under the binary name (SuperAudioApp) and once under the SwiftUI MenuBarExtra label (SuperAudio). Renaming the SPM executable target and the entry-point file collapses these into a single entry. Worth doing now while the change is cheap; would be painful at v1.0 when bundle identifiers are baked into license keys.

Filter belongs in the UI, not the discoverer

First pass had AirPlay1Discoverer skipping Macs/iPhones/iPads. Cleaner: emit every device, expose SinkDescriptor.isLikelySpeaker as a computed property in Core, let the menu bar default to filtering but allow toggle. Diagnostics get the full list; users get the clean one. Same data, two views.

8What's next

From "we can see speakers" to "audio comes out of one."

Step 1 · this week
RTSP OPTIONS handshake
First real protocol code that talks to the A7. Open a TCP socket, send OPTIONS * RTSP/1.0, parse the response. No audio yet — just confirming we can speak RAOP.
Step 2
ALAC encoding + RTP packetization
Take the captured PCM from CoreAudio, encode to ALAC via Apple's open-source encoder, packetize into RTP with RAOP's timestamp/sequence scheme.
Step 3
AES-128 session key handshake
Or skip it: the A7's TXT record advertises et=0,4, meaning it accepts unencrypted streams. Try clear first; only add encryption if the A7 rejects.
Step 4
Audio in the speaker
The Phase 1 demo gate: Spotify playing through Spacelab Forever Main Audio for 30 minutes with no drops.
Step 5 · Phase 2
Sync between A5 and A7
Master host-time, per-sink latency probe, schedule packets so both speakers hit "play sample N" at the same wall-clock moment. Walk between rooms — no flam.
Step 6 · Phase 3
Den joins the group
Sonos via UPnP/SOAP, local HTTP audio server, all three speakers in sync. Phase 1 → 3 audio gate.
